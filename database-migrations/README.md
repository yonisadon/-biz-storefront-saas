# Database migration directories

This directory contains legacy, one-off migrations for the original/central database schema. These files are **not automatically applied to each business-specific tenant database**.

For per-tenant schema changes:
- Add a numbered file matching `backend/migrations/tenant-NNN-name.sql`.
- Keep it additive and safe for existing rows.
- Apply it through `backend/src/tenantMigrations.ts`, which records successful migrations in each tenant database.
- Update `backend/migrations/tenant-schema.sql` for newly created tenant databases as well.
- Do not run legacy SQL against Railway or tenant databases without reviewing the target database and obtaining explicit approval.

## Tenant CRM, contact-flow and booking migrations

- `tenant-011-waitlist-lifecycle.sql` introduced a temporary 24-hour lead-retention deadline. It is historical migration code only: `tenant-012-configurable-retention.sql` removes its trigger/function and moves retention to the central platform policy matrix. Do not treat 24 hours as an active retention rule or reintroduce that trigger.
- `tenant-014-waitlist-crm-link.sql` adds a nullable technical `waitlist_entries.lead_id` foreign key with `ON DELETE SET NULL`. It never cascades deletion between waitlist and CRM.
- `tenant-016-retire-service-booking-trigger.sql` removes the old per-service booking-mode trigger/function. The legacy columns remain temporarily as read-only migration-compatibility data; the application no longer exposes per-service booking modes or uses them after `contact_options` has been migrated.
- `tenant-015-contact-options.sql` migrates legacy global CRM/WhatsApp flags and per-service booking settings into `config.contact_options`, with independent product and service settings. Legacy `free_datetime` and `availability` services map to business-level calendar-enabled services; in the new flow, customers can then choose a reserved appointment or a waitlist request. Legacy site-only service inquiries also map to calendar-enabled services when the old storefront was in catalog mode. If a legacy business has neither WhatsApp nor another valid route, migration defaults products to CRM website inquiry and services to calendar-enabled booking/waitlist so every catalog domain retains at least one valid customer path. These are intentional fallback defaults because the new model requires a valid route and has no generic site-inquiry route for services.
- `tenant-016-retire-service-booking-trigger.sql` removes the old per-product booking-mode trigger/function. The legacy columns remain temporarily as read-only migration-compatibility data; the application no longer exposes per-service booking modes or uses them after `contact_options` has been migrated.
- `tenant-017-decouple-appointment-crm-link.sql` changes the optional `appointments.lead_id` foreign key to `ON DELETE SET NULL`, so deleting a CRM lead never deletes its calendar appointment.
- CRM leads, appointments and waitlist requests have independent statuses, retention and deletion. Their nullable links are technical only; deleting one record type only nulls links from surviving records.

The `migrate-tenant-schemas` command preflights all mapped tenant databases first. It performs a dry run by default. Actual changes require both `APPLY_TENANT_MIGRATIONS=true` and `TENANT_MIGRATION_BACKUP_CONFIRMED=true`, after a restorable backup has been verified and explicit approval has been granted.


## Central Platform Registry migrations

- Central Registry migrations live in the numbered files `backend/migrations/000_tenant_registry.sql` through `backend/migrations/007_platform_push_retention.sql`.
- Migration 003 creates the super-admin-controlled retention matrix by plan/type/status. `standard` (Basic) defaults to 60 days for open CRM leads, 30 days for closed CRM leads, and one day for ended/cancelled appointments and expired/closed waitlist entries. `plus` defaults to no automatic deletion for CRM and calendar records. Migration 007 adds an independent Push-history policy for each plan; both plans default to 30 days for completed events. These values are editable in `/platform-admin/retention`; runtime reads the central policy table.
- They are **not run during API startup or Railway restarts**. The API's `prestart` migration hook has been removed.
- Run them only through the manual GitHub Actions workflow **Platform registry migrations**. The workflow takes a database preflight, serializes concurrent runs with a PostgreSQL advisory lock, and records completed files in `public.platform_registry_schema_migrations`.
- If there are no pending Registry migrations, the workflow exits without changing the database and without requiring backup approval.
- If changes are pending, each workflow run requires one explicit choice: confirm a restorable Registry backup was created and verified, or explicitly approve proceeding without a backup. The no-backup approval is scoped to that single manual run; automatic pushes/deployments cannot authorize it.
- The workflow uses the privileged `DATABASE_ADMIN_URL` connection but forces its database name to match `SUPERADMIN_DATABASE_URL`, preventing an accidental migration of the default `postgres` database.
- Do not run these SQL files manually or reintroduce them into `prestart`. New Registry schema changes must be added to the controlled migration list and the migration ledger.

- Migration 004, `backend/migrations/004_management_access_and_encrypted_tokens.sql`, adds encrypted permanent seller-link storage and the shared owner-session authorization function. It is registered in the controlled migration script and smoke-tested for idempotence. It is not applied during startup or deployment.
- Before deploying code that creates or redisplays permanent seller links, configure the dedicated `MANAGEMENT_TOKEN_ENCRYPTION_KEY` backend environment variable (64 hexadecimal characters representing 32 random bytes). Keep it stable and do not reuse other encryption or API secrets.
- Migration 005, `backend/migrations/005_seller_onboarding_state.sql`, stores whether a business completed the guided seller setup. Existing businesses are backfilled as already onboarded only when the column is first introduced; rerunning the migration does not mark newly created businesses as complete.

- `tenant-018-customer-device-push-consent.sql` renames per-booking capability/consent tables to target-link terminology and adds persistent operational consent scoped to one tenant and one browser subscription. It deliberately does not promote historical per-target opt-ins into persistent device consent. Fresh tenant creation runs the same numbered migration chain; because the initial Push settings backfill runs before the tenant business row is inserted, provisioning must create the tenant's `push_settings` row after inserting that row.
- `tenant-019-push-retention-index.sql` adds a partial index for completed Push events with a processing timestamp, allowing retention cleanup to find expired history without scanning pending/retrying events.
- `tenant-020-media-deletion-tracking.sql` adds `media_assets.deleted_at` and a partial index. Image uploads first persist a pending media row, then activate it only in the same DB transaction that links the asset to a product/gallery entry. Catalog deletes mark an unreferenced asset before attempting object-storage removal; the row is removed only after storage confirms success. The scheduled cleanup job retries pending deletions in bounded batches after a 15-minute grace period, preserving the storage key across upload crashes, transaction rollbacks and transient provider/database failures. Business deletion continues to include these rows in its persisted media manifest. The cleanup service must have the same explicit `STORAGE_DRIVER` and corresponding storage configuration as the API; it fails closed rather than falling back to local storage when that setting is absent.
- `tenant-021-appointment-blocks-range-index.sql` adds a GiST expression index on the exact `tstzrange(start_at, end_at, '[)')` expression used by availability overlap checks. The tenant migration smoke test verifies that PostgreSQL can select this index for the overlap predicate in a disposable database.
- `tenant-022-restrict-tenant-rls-policy-roles.sql` recreates the waitlist and Google Calendar tenant-isolation policies explicitly `TO app_runtime` instead of the broader default `PUBLIC` role. The migration is idempotent and the tenant migration smoke test verifies the policy roles.
- Retention cleanup requires the Push outbox/delivery and renamed target-link tables. It defers deletion of an appointment or waitlist target while any related Push event or delivery remains pending/processing, then removes target links and short-lived capabilities after the target is safely deleted. Completed Push outbox events and their cascading delivery history are retained according to the per-plan `push:completed` policy, measured from `processed_at`; pending/processing events or deliveries are never removed by this policy. Device-level consent remains independent of individual targets.
- Business provisioning spans the central Registry and a dedicated tenant database and therefore uses compensating cleanup rather than a cross-database transaction. If compensation fails, the business must remain suspended and mapped for operator recovery; never silently delete the Registry row while leaving an untracked tenant database.
- Business deletion is a resumable, destructive workflow: it requires an approved request and an explicit verified-backup attestation, persists the tenant database/media cleanup manifest before deleting external objects or dropping the tenant database, serializes concurrent executions per request, and only then removes the central business record. Failed steps must remain retryable; do not run this workflow against Production without explicit approval.
